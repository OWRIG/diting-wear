# 家里 Mac：给转写服务加上"区分说话人"

> 写给**家里那台 Mac 上的 AI 助手**。前提：转写服务已经按 [mac-asr-deploy-guide.md](mac-asr-deploy-guide.md) 部署好，正在运行（Qwen3-ASR 1.7B + Silero VAD，min_silence 0.8）。

## 目标

用户想知道每句话**是谁说的**。分工如下：

| 谁 | 负责 |
|---|---|
| **你（转写服务）** | 在**单个录音文件内部**区分说话人：给每个片段标上本文件内的说话人编号（0、1、2…），并输出每个说话人的**声纹向量** |
| 取件程序 `mac/worker.py`（另一个 AI 写） | 把各个文件里的声纹和历史声纹比对，给出全局编号（`spk_001`…），同步名字 |
| 手机 App | 用户在手机上给说话人起名字、合并重复的人 |

**声纹向量只能留在这台 Mac 上**：只通过 `127.0.0.1` 返回给取件程序，不上传到任何地方，也不写进 git。

## 硬性规则

和之前一样：不调用云端 API，只监听 127.0.0.1，模型放在 `~/models/`。另外：
- **`/transcribe` 原有的字段不能改也不能删**，只能新增字段。取件程序和手机都依赖现有格式
- 说话人分离出错时，**不能让转写失败**。退回到"整段都是说话人 0"，并在返回结果里加上 `"speaker_error": "原因"`

## 怎么做（建议方案，你可以根据实测调整）

用 **sherpa-onnx 自带的离线说话人分离**（`OfflineSpeakerDiarization`）：
- 分段模型：`sherpa-onnx-pyannote-segmentation-3-0`
- 声纹模型：优先用**中文训练的 3D-Speaker 模型**，比如 `3dspeaker_speech_campplus_sv_zh-cn_16k-common.onnx`（CAM++，192 维）。sherpa-onnx 的 speaker-recongition-models 发布页里有。下载走 GitHub 时如果卡住，可以去 ModelScope 找同一个模型
- 文档：k2-fsa.github.io/sherpa/onnx/speaker-diarization/ 。用法以官方文档和源码为准，不要凭记忆写

流程建议：
1. 对整段音频（16kHz）跑说话人分离，得到 `[(start, end, speaker_local)]`
2. 把 VAD/ASR 的每个文字片段，按**时间重叠最多**的原则分配一个本地说话人。如果一个片段跨了两个人，又能在说话人切换的时间点把片段切开重新识别，就切开；做不到就按重叠最多的算
3. 对每个本地说话人，取他所有语音（**总时长少于 1.5 秒的不算**，声纹不可靠），用声纹模型提取 embedding，求平均，再做 **L2 归一化**
4. 聚类数量：`num_clusters` 设为 -1（自动），聚类阈值先用默认值，在用户的录音上实测后再调整。**宁可把一个人分成两个，也不要把两个人并成一个**，因为用户在手机上可以把两个合并，但没法把一个拆开

## 返回格式（在原有的 JSON 上新增）

```json
{
  "...原有字段...": "不变",
  "segments": [
    {"start": 3.20, "end": 9.85, "text": "今天下午三点开会。", "speaker": 0},
    {"start": 10.1, "end": 12.0, "text": "好的。", "speaker": 1}
  ],
  "speakers": [
    {"speaker": 0, "speech_s": 41.2, "embedding": [0.0123, -0.0456, "...共 192 个 float"]},
    {"speaker": 1, "speech_s": 6.3,  "embedding": ["..."]}
  ],
  "speaker_model": "3dspeaker_campplus_zh-cn"
}
```

- `segments[].speaker` 是**这个文件内部**的编号（整数）。没有可靠声纹的片段（说话人总时长 < 1.5 秒），`speaker` 设为 `null`
- `speakers[].embedding` 必须是 L2 归一化后的向量
- **同一台 Mac 上要一直用同一个声纹模型**。换模型以后，旧的声纹就没法比对了。如果以后要换，先告诉用户

## 验收

1. 用户之前录过的距离测试那种**单人录音**：所有片段都应该是 `speaker: 0`，或者绝大多数是 0
2. **两个人的对话**：请用户找人对话 1–2 分钟，或者用手机外放一段采访视频，同时开着设备录音。结果应该分出 2 个说话人，片段的分配大体正确
3. **同一个人在两段不同录音里的声纹**，余弦相似度应该明显高于**不同人之间的**。请把实测数值写进报告，比如"同一人 0.75–0.85，不同人 0.2–0.45"。取件程序要根据这个数值来定比对的门槛
4. 一段 5 分钟的录音，加上说话人分离以后，总处理时间增加了多少，写进报告
5. 说话人分离故意出错时（比如模型路径填错），转写照常返回，并带上 `speaker_error`

## 报告

完成后把以下内容发给用户：用了哪个模型、处理时间增加了多少、验收 1–5 的结果，**特别是第 3 条的相似度数值**。

## 最后：更新取件程序

转写服务改好、验收通过之后：
1. `cd ~/diting-wear && git pull`，拿到新版取件程序（`mac/worker.py` 和 `mac/speakers.py`，负责跨录音认人）
2. 根据验收第 3 条测出的相似度，在 `~/.config/diting/worker.env` 里加一行门槛：取"同一人的最低值"和"不同人的最高值"的中间。比如同一人 0.75–0.85、不同人 0.2–0.45，就写 `SPEAKER_THRESHOLD=0.6`
3. 重启取件程序：`launchctl kickstart -k gui/$(id -u)/io.github.owrig.diting.worker`
4. 看日志 `tail -f ~/diting/logs/worker.log`，下一段录音处理完后应该能看到"新说话人 spk_001"
5. 本地数据库 `~/diting/diting.db` 里的 `speakers` 表存的是声纹，**不要上传、不要备份到云盘**
